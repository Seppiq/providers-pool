# http-providers-pool

Сервис-реестр HTTP-клиентов поставщиков: по id поставщика и номеру телефона
возвращает, доступен ли номер. Не веб-приложение — OAuth, ретраи и база
по ТЗ не нужны.

## Как устроено

Spring-приложение без web-стартера, точка входа — `ProvidersApplication`. Слои:

- `domain` — `Provider` (id, baseUrl, apiKey). Immutable record, у baseUrl срезаются
  завершающие слэши, чтобы URL запроса не получился с двойным слэшем;
- `source` — `ProviderSource` и его реализация `JsonFileProviderSource`: чтение набора
  поставщиков из json-файла и сохранение изменений обратно;
- `service` — `ProviderRegistry` (реестр по id, набор меняется целиком) и
  `PhoneAvailabilityService` (фасад над реестром и клиентом). Если поставщик не найден —
  `ProviderNotFoundException`;
- `client` — `ProviderClient` / `HttpProviderClient`, сам запрос к поставщику;
- `configuration` — сборка бинов, путь к файлу задаётся свойством `providers.json-file`.

## Файл поставщиков

Набор поставщиков — один json-файл, путь в свойстве `providers.json-file`. По умолчанию
это [providers.json](providers.json) в рабочей директории (`file:providers.json`).
Вместо `file:` можно указать `classpath:`, но ресурс внутри jar доступен только для
чтения — заменить набор через него не выйдет, при попытке будет ошибка с пояснением.

```json
[
  {"id": "provider-a", "baseUrl": "https://a.example.com", "apiKey": "key-a"}
]
```

## Замена набора

`ProviderRegistry.replaceAll(List<Provider>)` меняет весь набор целиком. Сначала новый
список валидируется (дубликаты id отклоняются ещё до записи), затем пишется в файл
и только после успешной записи подменяется в памяти. Ошибка на любом шаге оставляет
прежний набор на месте и доходит до вызывающего кода.

Про параллельность: замены идут по одной (synchronized), читатели видят либо старый
набор, либо новый — никогда смесь. Файл пишется во временный файл в той же директории
и подменяется переименованием, «наполовину записанным» он остаться не может.

## Запрос к поставщику

`GET {baseUrl}/subscribers/{phone}`. API-ключ — в заголовке `X-API-Key`
(в ТЗ способ передачи не уточнён, здесь зафиксирован такой вариант).

- 200 и `{"status":"ok"}` — номер доступен
- 404 — недоступен
- 200 с пустым телом или другим статусом — тоже недоступен
- остальные HTTP- и сетевые ошибки пробрасываются вызывающему коду как есть

Таймауты: 5 секунд на соединение, 10 на чтение — тест следит, чтобы это обещание
не разошлось с properties.

## Подводные камни

Коротко о том, где ТЗ умалчивает и почему сделано именно так.

- **Куда класть API-ключ** — в ТЗ не сказано. В заголовок, не в URL: URL попадает
  в логи и метрики, ключ — нет.
- **Телефон в URL** — подставляется через URI-шаблон, а не конкатенацией: иначе
  `+7999...` или пробел соберут битый запрос. Плюс у `baseUrl` срезаются хвостовые
  слэши, чтобы не было двойного слэша в пути.
- **404 vs остальные ошибки** — граница тонкая: 404 это штатное «недоступен», всё
  прочее глотать нельзя. Ловим только `HttpClientErrorException.NotFound`,
  остальное уходит наверх как есть.
- **200 с некорректным телом** — если тело пустое или `status` не `ok`, это
  «недоступен». А вот 200 с не-JSON телом (типичная заглушка прокси) — ошибка
  парсинга и она пробрасывается: молча превращать чужую аварию в `false` опасно.
- **Неизвестный id поставщика** — исключение, а не `false`: тихий `false` маскирует
  баги вызывающего кода.
- **Дубликаты id** — отклоняются с падением, и при старте, и при `replaceAll`.
  Реестр по id, поэтому два поставщика с одним id — это ошибка данных, а не «последний
  выиграл».
- **Таймауты** — в ТЗ про них ни слова, но без них зависший поставщик подвесит
  поток навсегда, а ретраев по ТЗ нет. Поэтому 5с/10с.
- **Файл читается один раз при старте** — hot-reload не нужен по ТЗ; чтобы подменить
  набор на живом приложении, есть `replaceAll`. Битый файл роняет старт сразу —
  падение при запуске честнее загадочного сбоя на первом запросе.
- **`replaceAll` пишет и в файл** — ТЗ требует только «заменить целиком», но если
  менять только память, файл и реестр разойдутся. Поэтому порядок такой: валидация →
  запись в файл → подмена.
